# 开发过程记录

本文档根据 docs/Agent Steps 目录中的过程截图整理，用于记录本次答题过程中的设计思路、AI 辅助介入点、实现顺序与关键修正。

## 1. 开发目标拆解

根据题目要求，项目需要完成三部分能力：

1. 用户注册、登录、Token 鉴权与受保护的 Hello World 接口。
2. 图片上传，并对图片执行 RGB -> BGR 通道互换后落盘。
3. 受保护的异步并发聚合接口，支持异常隔离、超时与结果汇总。

在开发过程中，优先保证骨架可运行、测试可执行，再逐步补齐业务接口与文档。

这一阶段先通过 AI 辅助确认基础技术路线，核心决策如下：

随后按分层结构初始化项目骨架，创建 app、sql、docs、tests、uploads 等目录，并补齐：

- Tortoise ORM 配置。
- docker-compose.yml，便于本地启动 MySQL。
- 启动测试与基础健康检查测试。

这一阶段的目标不是一次性实现全部业务，而是先让服务能启动、配置路径明确、测试具备落脚点。

第二阶段围绕数据结构展开，主要处理三件事：

这个阶段的重点不是“先写接口再补表”，而是先把数据契约与数据库映射关系稳定下来，减少后续启动期和测试期的结构性错误。

### 阶段四：登录、鉴权与统一时间处理

对应截图：011、013、014

![011](Agent%20Steps/011.png)
![013](Agent%20Steps/013.png)
![014](Agent%20Steps/014.png)

登录接口阶段的核心要求是：仅传 username 与 password，其中 username 既可以匹配用户名，也可以匹配手机号或邮箱。

这一阶段的实现重点包括：

- 新增登录接口与对应测试。
- 复用密码哈希校验逻辑。
- 将登录查询扩展为 username/phone/email 三字段匹配。
- 生成带过期时间的访问凭证。

随后又补上了 token 校验装饰器，用于：

- 从请求头读取 token。
- 校验 token 是否存在、是否过期。
- 基于 scope 控制不同接口的访问范围。
- 在失败时返回统一格式的错误响应。

在这一步开发后期，发现鉴权过期判断存在时间基准不统一的问题，即本地时间与 UTC 时间混用。为此统一抽取了 UTC 时间工具方法，替换掉零散的 datetime.now() +/- timedelta(...) 写法，确保：

- token 签发时间与过期时间计算一致。
- 模型测试、鉴权测试与业务实现的时间基准一致。
- 后续扩展 refresh token 或更多鉴权逻辑时不会继续放大时区偏差问题。

### 阶段六：图片上传与 RGB -> BGR 通道转换

对应截图：016、017

![016](Agent%20Steps/016.png)
![017](Agent%20Steps/017.png)

上传接口阶段，先实现流式文件上传，并在请求进入时基于 Content-Type 做 MIME 白名单校验，仅允许：

- image/png
- image/jpeg

后续又针对图片处理逻辑补上通道转换装饰器，在落盘前执行 R 与 B 通道互换。这个阶段有一个关键修正点：

- 原测试若使用伪造图片头，Pillow 无法稳定解码，不能证明真实的图像处理正确。
- 因此改为使用真实可解码 PNG/JPEG 样本验证上传与 RGB -> BGR 的效果。

这一调整保证了测试覆盖的是“真实图像处理链路”，而不仅仅是“字节写盘成功”。

### 阶段七：异步并发聚合接口与异常处理

对应截图：018、020、021、022

![018](Agent%20Steps/018.png)
![020](Agent%20Steps/020.png)
![021](Agent%20Steps/021.png)
![022](Agent%20Steps/022.png)

最后实现题目第三部分的异步聚合能力。开发顺序上先加接口占位，再补实际异步任务与异常控制。

这一阶段的关键点包括：

- 新增异步整数参数接口，并对参数范围做校验。
- 引入异步模拟任务，执行随机时长的 CPU 密集型模拟工作。
- 将任务并发收集接入聚合接口，而不是顺序 await。
- 为单任务增加超时设置，超时后将异常上抛，由聚合层统一转换为失败结果。
- 为模拟任务增加随机失败能力，并通过测试固定随机值验证失败分支。
- 使用聚合层统一汇总成功结果、失败结果与异常信息。

从截图可以看出，这一阶段并非只实现 happy path，而是专门补了：

- 超时场景。
- 随机失败场景。
- gather 返回异常联合类型后的静态类型修正。

因此并发接口最终不仅能跑通，也具备了题目要求的异常隔离能力。

## 3. 开发过程中的关键设计取舍

### 先骨架后业务

没有一开始就把三道题一次性写完，而是先保证：项目结构、依赖、配置、数据库连接方式、启动验证和测试基座都成立。这样后续每新增一段业务时，都能快速做局部验证。

### 先测试落点，再推进接口

从截图可见，多次采用“先补最小测试或最小可验证入口，再落代码”的策略。这种方式适合当前题目，因为接口要求清晰、验收边界明确，测试能快速暴露回归问题。

### 对时间与异常做统一收口

本项目的两个高风险点分别是：

- Token 过期判断的时间基准。
- 并发任务的异常与超时传播。

开发过程中都选择做“统一收口”：

- 时间统一走 UTC 工具方法。
- 并发异常统一由聚合层汇总，不在单任务内部静默吞掉。

这样后续维护时，问题定位更集中，也更符合题目对异常处理和明确错误信息的要求。
